3. ASSET GENERATION — GOOGLE FLOW / VEO (NOT Higgsfield/Seedance)
Reason for switch: cost (Excel/token-heavy approaches rejected; Flow is cheaper), despite Flow having no MCP. Current workflow is hybrid: Claude writes the prompts → user generates manually in Flow → uploads MP4s → pipeline extracts frames. Veo API (Vertex AI / Gemini API) is the future automation path.
Confirmed Veo 3.1 / Flow capabilities (verified July 2026):

Ingredients to Video: up to 3–4 reference images to lock character/object/style identity (Veo 3.1: 8s only, Lite/Fast; Gemini Omni Flash: 4/6/8/10s + character/avatar & audio refs)
Frames to Video: explicit start frame + end frame (Veo 3.1, 4/6/8s). Omni Flash multi-frame with transition instructions works live despite docs saying "coming soon"
Extend: continue from the last second of a previous clip (8s clips only)
720p/1080p (always use 1080p), 16:9 or 9:16, ~8s clips, native audio (always prompt "no dialogue, no music" and strip audio anyway — Flow downloads still carry an AAC track; strip with ffmpeg -i in.mp4 -an -c:v copy out.mp4)
Duration is set in the prompt-box settings (UI), not by writing "8 seconds" in the prompt text
Image models in Flow: Nano Banana 2 (default), Nano Banana Pro (Ultra), Imagen 4. In lab/001 comparisons all three produced usable stills; pick by composition fit, not model

The established asset generation order (NON-NEGOTIABLE, per Russ):

Lock character identity first — triptych (front, three-quarter, back) + portrait still ("Asset 0"). Iterate stills until likeness is confirmed BEFORE spending video credits.
Generate empty scene plates second — clean environments with NO character in them.
Composite character-into-scene as a STILL third.
Animate last, using that composited still as the start frame (Frames-to-Video where needed).

Scene-first, character-composited-second. Never generate character-in-scene directly.
Hard-won prompt-engineering rules (do not relearn these):

Triptych outperforms a single reference image for multi-angle consistency. Feed it as the first ingredient in every generation.
360° orbits: never one clip. Two chained 180° clips via Frames-to-Video with explicit front + back anchor stills. Single image + motion text makes Veo hallucinate environment or rotate the subject instead of the camera.
Camera instructions must be isolated, first, and use professional terminology. Lead with a named camera move in its own sentence (e.g., "Camera: 180-degree arc dolly-out shot"), then explicit exclusions ("the subject does not rotate, spin, or turn; only the camera moves"). Descriptive prose fails.
No readable text in any shot (AI text = gibberish; real text is overlaid in HTML).
Always append: "No dialogue, no music. No warping, no morphing, no extra limbs."
End frame for the Builder arc dolly-out = wide lateral profile shot, camera exactly 90° to the subject (not over-the-shoulder, not behind).
(lab/001) Same-scene multi-frame trick: when using multi-frame/frames-to-video for a single camera move, derive the end frame FROM the start frame via image edit (crop/push-in/"camera moved forward") — frames must differ by camera position only, never by content, or the model invents a hidden cut/second move.
(lab/001) Style-hold clause, not style stack, in motion prompts: the start frame carries the look; re-describing the full aesthetic makes the model re-render instead of animate. Add one sentence: "Maintain the exact color grade, depth of field, and film grain of the provided frame — do not brighten or clean up."
(lab/001) Reference images bleed content, not just grade: when referencing a still only for its look, state "use reference ONLY for color grade, lighting character, and grain — different scene: no <objects from reference>."
(lab/001) Pick stills geometry-first: the composition must physically support the single permitted camera move (e.g., a dolly-forward needs a walkable aisle). A prettier still with blocked geometry forces the model into crane/warp moves.
(lab/001) Don't prompt people/objects into video that aren't in the still (e.g., a bartender with no bar in frame) — the model invents objects mid-clip. Use what the still contains, constrain its motion instead.

4. THE FLIPBOOK METHOD — TECHNICAL SPEC (for scroll-scrubbed heroes)
Never scrub <video> via currentTime — CPU seek-choking, stutter, mobile crashes.
Pipeline: MP4 → FFmpeg → .webp image sequence → single <canvas> scrubber.

Extraction: ffmpeg -i clip.mp4 -vf "fps=24,scale=1920:-1" -c:v libwebp -q:v 75 assets/sequence_name/frame_%04d.webp
Naming convention: /assets/sequence_name/frame_0001.webp
Exactly ONE <canvas> element as the visual engine; if full-page: position: fixed; inset: 0; width: 100vw; height: 100vh; z-index: 0; pointer-events: none;
Frame budgets: hero sequence 20–24 fps (~320–380 frames for a chained orbit), secondary scenes 12–15 fps (~100 frames), webp q≈65–75
Mobile: half-resolution frame set, selected by viewport width
Preload hero sequence; lazy-load secondary sequences; poster still shown while loading
Target payload: hero sequence ~8–15 MB after compression
Black-void backgrounds compress far better in webp — favor them
Lenis smooth scroll; text reveals pinned to scroll position
QA: step the chained-clip seam frame-by-frame; trim warped first/last frames before extraction

4a. AMBIENT-LOOP PATTERN (for loop archetypes, e.g., 05 restaurant)
When the hero is an ambient mood loop (not a scroll-driven camera journey), use native <video>: muted, autoplay, loop, playsinline, preload="metadata", poster = extracted first frame. Poster is the LCP; video swaps in after paint. Lazy-load below-fold videos (IntersectionObserver). prefers-reduced-motion → posters only. Mobile variants via source switching. Aspect-ratio boxes → zero CLS. Choose flipbook vs loop per archetype, not by default.
